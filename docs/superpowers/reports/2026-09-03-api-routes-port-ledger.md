Findings acted on:
  1. IMPORTANT pets/[id]/route.ts:36-40 destroy-then-upload. If uploadPetPhoto throws AFTER destroyPhoto succeeded, the old image is permanently gone from Cloudinary while foto/public_idfoto still point at the dead URL - a broken image on the public page, and a 500 the admin reads as "nothing happened". Express has the same bug, but the stub never failed and real Cloudinary does (rate limits, timeouts).
     Ruling: REORDER to upload-before-destroy despite the port-identical decision. That decision was about not silently hardening SECURITY flaws; this is irreversible data loss of a charity's pet photos, a different category. Failing the other way merely orphans an image in Cloudinary, which is recoverable. Recorded so the user can revert. Cost if wrong: an orphaned image when destroy fails after a successful upload.
  2. IMPORTANT Navbar verifyToken() calls GET /api/usuarios, which is unauthenticated and therefore ALWAYS succeeds. Two consequences: the navbar downloads the entire user table including bcrypt hashes on every "Gerenciar" click, and after the 7-day cookie expiry localStorage still says logged-in, so the navbar shows admin links forever and clicking them bounces to /painel with no explanation.
     Ruling: repoint verifyToken() at POST /api/usuarios/atualizatoken. Frontend-only change, so it does not touch the ported API behaviour; it makes the check real, renews the cookie, fixes the day-7 phantom-admin state, and stops the hash dump from the public site's own navbar.
  3. MINOR cloudinary.ts has no upload timeout; a hung request holds the function to maxDuration. Folding a timeout into the same wave.
Deliberately NOT changed: `details: error.message` echoing raw Prisma text on two 500s. The reviewer suggested removing it, but that IS ported API behaviour and the user's port-identical decision governs. Surfaced to the user instead.
NOT FIXABLE FROM HERE - highest production risk: Vercel caps function request bodies at 4.5 MB while the old Express host had none. PetForm posts the raw File with no resize, so a normal phone photo (4-12 MB) gets a platform 413 BEFORE the handler runs, showing the form's generic error. This is the admin's primary action and no local test could see it. Must be tested on the Preview URL with a real large photo.
Cross-cutting IMPORTANT, not a regression: two contradictory definitions of "active pet" - pets.ts uses the OR with isSet:false, while busca and [id] inline the bare deleted_at: null. A legacy document with no deleted_at key would list on the home page but 404 on GET by id and return {count:0} on PUT. Byte-identical to Express, so already true in production. One countDocuments({deleted_at:{$exists:false}}) against Atlas settles whether it matters.
